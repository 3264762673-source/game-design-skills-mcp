# 像素游戏 UI 布局、图标按钮与页面交互：证据与决策卡

研究日期：2026-11-09。用途：为三个独立 Skill 提供证据、候选规则及可执行检验。本文完成的是跨作品案例检查，未运行这些游戏，未做真人实验、计时任务或可用性因果验证。

## 结论与准入范围

可以进入技能的核心方法是：按当前玩家决策分配屏幕；把图标的含义、视觉状态与可点击区域分别设计；把页面转换写成有输入、结果及返回位置的状态表。**作品中的存在只能支持“该做法在这些情境中可行”，不能证明采用后一定更好。**

本次较充分的跨作品支持集中在 L1 信息分区、I1 图标与可查名称配合，以及收窄后的 X2 决策信息预览。L2 跨设备重排只有一个直接开发者案例；L3 像素比例属于制作约束；I2 全状态、I3 命中区、X1 焦点恢复、X3 输入可达性仍需运行测试。后者可作为有标准依据的验收要求，不能标成“多个像素游戏实测成立”。

## 起源、定义与边界

- 历史线索：1982 年原作者对 Xerox Star 的说明已经把位图显示、熟悉的物体图标、窗口、任务分析和一致的操作模型联系起来。[S01](https://guidebookgallery.org/articles/historical/designingthestaruserinterface/) 这是通用 GUI 的可追溯前史，不是“像素游戏 UI 发明于 1982 年”的证据。本次未建立完整的游戏 HUD 史。
- 本研究对**像素游戏 UI 布局**的工作定义：安排决定当前行动所需的信息、操作入口和游戏画面，并声明每层的显示比例；像素外观不决定信息结构。
- **Icon / 小按钮美术**：icon 是代表对象、功能或状态的视觉符号；button 是接受某种输入并触发行动的控件。一个 icon 可以不接受点击，一个 button 也可以只含文字。背包里的多格物品还可能承载空间规则，不能一概套用方形工具栏图标模板。
- **UI / 页面交互逻辑**：记录屏幕状态、焦点、输入模式、可用操作、动作结果、取消路径和恢复位置。漂亮的静态页面不能证明这些逻辑成立。
- **三个坐标单位必须分开**：资产源像素、最终显示像素/逻辑单位、交互命中区。WCAG 的 CSS px 不能直接写成 Aseprite 的源像素数。

### 像素游戏 UI 布局

#### L1 — 先确定当前决策所需内容，再分配区域

1. **触发条件**：玩家为一次决定在多个角落来回找目标、成本、后果；或者菜单占用了需要观察的游戏区域。
2. **候选解释**：信息分组错误、当前对象没有明确标识、无关内容抢占空间；也可能是规则没讲清而非布局问题。
3. **检查方法**：写出一个具体任务，例如“选物品并判断对本回合的帮助”；将所需信息标成当前对象、长期状态、条件详情三类；在真实分辨率截图标出每次查找点。先检查数据是否真的存在。
4. **可执行修改**：固定长期状态的相对位置；把当前对象及其详情建立清楚对应；按任务切换主要工作区。对比操作所需的信息尽量同屏或保留可恢复的参照，而不是机械追求最少元素。
5. **不适用情况**：隐藏信息本身就是谜题；桌面整理、空间记忆是玩法。不能以“整洁”为由消除玩法约束。
6. **预期变化**：减少找错对象、漏看成本和无目的跨区扫视；只是设计预期，未实测。
7. **验证与撤回**：用原版/修改版执行同一组正常、满背包、长文本任务；记录漏项、操作完成、遮挡。若查找改善却使比较信息不可得，恢复旧分区并改为按需详情。不要只问“更好看吗”。
8. **来源与状态**：[S02](https://media.gdcvault.com/gdc2019/presentations/Into%20the%20Breach%20Postmortem%20Final.pdf)、[S03](https://papersplea.se/)、[S10](https://store.steampowered.com/app/1970580/Backpack_Hero/) 的观察启发；执行步骤为本次推导。跨作品案例支持，无因果证明。

#### L2 — 屏幕改变时重排任务，保留不可丢失的比较关系

1. **触发条件**：把桌面 UI 缩到手机/掌机后，文字、点击或并列比较无法完成。
2. **候选解释**：不只是字体小，可能是横屏任务空间与竖屏输入方式冲突。
3. **检查方法**：列每个任务需要同时看见的对象、可轮换查看的对象及手指遮挡区域；用最终屏幕尺寸检查，不拿编辑器放大图验收。
4. **可执行修改**：先重排区域、页签和详情，再调整画布比例；可采用缩略导航加大图详情。为需要跨文书比较的任务保存选中、位置或摘要，明确失去的同时可见性。
5. **不适用情况**：空间摆放本身决定效果时，不可自动整理成列表。Backpack Hero 的多格物品直接构成此边界。
6. **预期变化**：能读、能选，同时保留原任务所需信息；并不保证保留所有原作操作体验。
7. **验证与撤回**：在目标设备完成相同复杂任务，记录误点与反复切页；若变成依赖记忆的来回切换，恢复并列比较、摘要或暂存区。是否采用触控字号/目标尺寸应另验。
8. **来源与状态**：[S04](https://dukope.com/devlogs/papers-please/mobile/) 的作者实践，C 提供适用边界；**单个直接案例，待更多跨设备检验**。

#### L3 — 给每层声明像素与文字比例，按最终输出检查

1. **触发条件**：同一图标出现粗细不一、字形发糊、缩放后边框跳动；或为了统一像素尺寸让文字小到不可读。
2. **候选解释**：非预期采样/变换、源分辨率不一致、屏幕适配与局部排版冲突。
3. **检查方法**：分别登记世界、UI框、图标、文字的源尺寸和最终倍率；看 100% 最终输出和移动过程，而非只看最近邻放大的静帧。
4. **可执行修改**：以层为单位约束比例与对齐；静态边框/图标先做整数落点；文字可采用独立可读比例。任何分层例外写入规范并附最终设备截图。
5. **不适用情况**：不把“全游戏必须同一像素大小”“所有像素游戏只能最近邻”设成审美定律；已有开发者使用混合比例与最终滤波。
6. **预期变化**：减少非预期形变并保留可读性；不是像素越粗越好。
7. **验证与撤回**：检查窗口、全屏、不同缩放与长文本；若改动只改善放大截图却降低真实阅读，撤回该层缩放。不同设备应各留基准图。
8. **来源与状态**：[S04](https://dukope.com/devlogs/papers-please/mobile/) 提供反例；具体管线检查为工程推导。**原“全局单一比例”主张撤回，替代规则待测**。

### 像素游戏 icon / 小按钮美术

#### I1 — 测试功能含义和同组混淆，而不只测试“像什么”

1. **触发条件**：画得像物体，玩家仍不知道按下会做什么；或多个技能/状态图标彼此混淆。
2. **候选解释**：形状分辨不足、图与功能的关系太远、名称不熟悉；三者需要分别检查。
3. **检查方法**：在完整同组图标中做“功能→选择”和“图标→解释”两种任务；分首次见到和学习后记录；分别比较纯图、图加名称，不把个人审美评分当辨识率。
4. **可执行修改**：优先改变决定功能差异的轮廓/内部标记；陌生、高后果命令保留文字或焦点/悬停/触控可打开的说明。物品图可保留世界内形象，但复杂效果用说明承载。
5. **不适用情况**：已学习且高频使用的通用操作不一定需要常驻长标签；依靠物品占格形状的玩法不能统一裁成相同方形。
6. **预期变化**：降低同组误认和首次误用；熟练用户可能需要更紧凑呈现。
7. **验证与撤回**：用未参与设计的人测试；按错误对记录混淆矩阵。若去细节损失类别区分，恢复识别特征；若标签遮挡任务区，改为可按需读取而非删除说明。
8. **来源与状态**：[S08](https://link.springer.com/content/pdf/10.3758/BRM.41.2.325.pdf) 的图标学习研究可迁移，A/B/C 是案例支持；**论文不是像素游戏实验，图标越简单越好不获支持**。

#### I2 — 状态变化应传达状态名，不能只做装饰变色

1. **触发条件**：玩家分不清悬停、键盘焦点、选中、禁用、冷却或目标预览。
2. **候选解释**：状态混用同一高亮、只靠色相、缺少禁用原因，或者输入状态实现错误。
3. **检查方法**：做逐状态接触表；写每个视觉状态实际代表的系统状态。黑白/色觉模拟只能作为筛查，还需在实际背景和尺寸上检查。
4. **可执行修改**：为焦点配置清楚轮廓，为选中添加持续标记，为禁用/冷却提供原因或进度；颜色之外增加可辨的形状、文字或明暗关系。图标含义与当前状态分别编码。
5. **不适用情况**：没有某状态的控件不必造出全套状态；无信息含义的装饰色不必添加文字。
6. **预期变化**：能说明“哪里有焦点、什么已选、为何不能按”；不承诺改善战斗胜率。
7. **验证与撤回**：从鼠标移入切到手柄，再打开/关闭模态层；检查有无双焦点或丢焦点。若边框遮住小图特征，移到容器边界；若变暗文字不可读，恢复文字对比并另加禁用标识。
8. **来源与状态**：[S06](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)、[S07](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/112) 支持验收原则；A/C 只支持局部视觉做法。**完整状态及其行为待测**。

#### I3 — 把小像素图与交互命中区分别交付

1. **触发条件**：按钮图很清楚却常误触、点击无响应，尤其在掌机/手机或密集工具栏。
2. **候选解释**：命中区太小/重叠、输入穿透、控件禁用，或系统实际没有收到输入。
3. **检查方法**：打开 hitbox 调试层并记录 pointer-down、目标解析及结果；检查实际逻辑尺寸、间距、层级和边缘点击，而非只量源 sprite。
4. **可执行修改**：给 sprite 增加容器内边距并明确 hit bounds；密集处增大间距或重排；相邻目标避免不明确重叠；另给键盘/手柄可达路径。素材清单同时交付 visualBounds 和 hitBounds。
5. **不适用情况**：点选网格坐标本身是玩法时，不能任意膨胀至覆盖邻格；可提供缩放或辅助选择。WCAG 2.5.8 还有间距、等效入口等例外。
6. **预期变化**：降低点到邻项和重复无效点击。
7. **验证与撤回**：对目标边缘、相邻目标和弹窗遮罩逐一输入；若扩大命中区造成邻项抢点，撤回扩大并调整布局。源像素和 CSS px 的数值不得直接相等。
8. **来源与状态**：[S05](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)：Web 指针目标 24×24 CSS px 为带例外的最低标准；不是所有游戏审美阈值，也不是足够舒适的普适尺寸。**工程要求，三个游戏均未测 hitbox**。

### 像素游戏 UI / 页面交互逻辑

#### X1 — 每次页面/模式转换都定义焦点所有者和返回位置

1. **触发条件**：开背包后角色继续移动；关弹窗后失去选中项；同一输入因隐蔽模式触发另一动作。
2. **候选解释**：输入未由当前模式消费、隐藏控件残留焦点、返回目标已删除或模式变化没有表现。
3. **检查方法**：写状态表：状态→允许输入→转移→当前焦点→退出后焦点；逐条走打开、确认、取消、关闭、对象删除和切设备路径。
4. **可执行修改**：模态层取得自己的输入上下文；记录来源控件，关闭后恢复至仍存在的来源或明确兜底项；让模式入口、当前工具、退出方式可见。游戏内拖拽模式与设置菜单可使用不同规则，但各自应明确。
5. **不适用情况**：无焦点指针界面不必强造手柄焦点；游戏刻意的模式谜题需另定理解目标。不能把所有模式都改成阻断游戏的弹窗。
6. **预期变化**：取消/返回后可继续原任务；减少误触背景与焦点丢失。
7. **验证与撤回**：做嵌套弹窗、长列表滚动、选中物品被消耗等序列测试。若恢复旧对象已无效，改到可预期邻项而非随机首页。输入日志存在穿透则先修逻辑，不能靠动画遮盖。
8. **来源与状态**：[S04](https://dukope.com/devlogs/papers-please/mobile/) 支持局部模式实践；[S14](https://docs.godotengine.org/en/stable/tutorials/ui/gui_navigation.html) 说明隐藏控件会失焦及初始焦点配置。**案例仅部分支持，状态机规则是待测工程推导**。

#### X2 — 当选择依赖后果时，让对象、成本与预期结果可检查

1. **触发条件**：玩家无法区分选择对象、预览行动与最终提交；或者只有提交后才知道原本应能得知的代价。
2. **候选解释**：信息缺失、预览对象错位、确认边界隐蔽；也可能是游戏有意保留不确定性。
3. **检查方法**：先由玩法规格说明哪些信息应已知；对照“当前对象→行动→成本→结果/未知范围”，检查界面是否错误暗示确定性。
4. **可执行修改**：把可知信息放在对象说明、范围/方向标记、成本提示中；预览与最终提交使用可区分状态。是否支持撤销由玩法决定，支持时明确撤销边界。
5. **不适用情况**：推理、赌博或隐藏信息玩法不能被 UI 自动揭底；具有节奏/责任感的盖章、出牌不能一律自动化或无代价回退。
6. **预期变化**：减少“以为点了另一对象/没想到要花这个”的误用，同时保留设计允许的不确定性。
7. **验证与撤回**：让测试者在提交前说明将发生什么，并区分故意未知；若提示剧透解题或撤销破坏资源压力，收窄到操作确认，不改玩法信息规则。
8. **来源与状态**：[S02](https://media.gdcvault.com/gdc2019/presentations/Into%20the%20Breach%20Postmortem%20Final.pdf)、[S04](https://dukope.com/devlogs/papers-please/mobile/)、[S10](https://store.steampowered.com/app/1970580/Backpack_Hero/) 支持不同情境。**收窄后有案例支持；“所有后果都预告/所有操作可撤销”撤回**。

#### X3 — 针对承诺支持的输入方式验证完整任务，而非只显示对应按键图

1. **触发条件**：游戏标称手柄或键盘支持，但菜单有只有 hover 才能出现的说明、不可达关闭按钮或导航死路。
2. **候选解释**：焦点邻接自动猜测不符布局、默认焦点缺失、绑定只覆盖主流程、输入提示没有随模式改变。
3. **检查方法**：从首次启动到设置、开局、库存、确认、取消及退出，用每一种承诺支持的输入单独完成；记录不可达控件和需要借用其他设备的步骤。
4. **可执行修改**：明确初始焦点、方向邻接及 Tab 顺序；统一确认/返回语义；给 hover 信息提供 focus/按键/触控替代路径；状态变动时维护邻接与滚动可见性。输入动词可一致，手势实现可以不同。
5. **不适用情况**：未承诺某设备不等于必须实现它；但一旦承诺，应明确哪些玩法环节有限制。地图或空间拼图不能硬套线性表单导航而破坏方向关系。
6. **预期变化**：单一输入能完成所承诺的全部核心任务，且返回/选择含义稳定。
7. **验证与撤回**：断开鼠标做键盘/手柄测试，反向测试触摸；加入列表为空、物品删除、弹窗关闭情况。若自动邻接跳跃，改显式邻接；不要以“商店有手柄标签”代替验证。
8. **来源与状态**：[S07](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/112)、[S14](https://docs.godotengine.org/en/stable/tutorials/ui/gui_navigation.html)。C 商店声明不能验证行为；**工程要求，跨作品运行测试尚未完成**。

## 论文与标准的具体贡献

[McDougall 与 Isherwood, 2009](https://link.springer.com/content/pdf/10.3758/BRM.41.2.325.pdf) 研究图标识别随学习变化的预测因素，区分图形、功能名称与二者关系；初学阶段语义距离较重要，后续功能熟悉度的作用增加。阅读范围为摘要、理论、方法及结果相关段落；不是对所有表格的重新统计。迁移到像素 UI 的建议是分别测试初学/熟练和同组图标，**不能从此推出某个固定颜色数、16×16 必然最优或删细节一定更易认**。

W3C 的目标尺寸和色彩标准以及微软 XAG 是可操作的无障碍依据，不是对像素美术审美优劣的实验；本文将它们用于菜单/控件验收。最终设备、引擎单位、平台要求和游戏中的空间任务需另作转换与适用性判断。

## 交给 Skill 编译环节的要求

1. 三个技能分别交付：布局规格（任务/区域/尺寸场景）、图标与状态表（语义/视觉边界/命中边界）、页面状态与导航图（输入/守卫/结果/返回位置）。
2. 每条输出附 `evidence_status`：`case-supported`、`practice-informed`、`standard-derived` 或 `project-tested`。本研究没有任何 `project-tested` 条目。
3. 数据/代码应允许配置比例、hit bounds、状态语义和输入映射，不把本报告中的例子写死成全游戏规则。
4. 新项目验收必须实际运行；先验证静态图能回答的问题，再测输入事件与焦点，最后才测玩家理解。每轮保留原版截图/状态表与回退条件。
5. 如发布要求是“每条都经过两个推导游戏和一个独立游戏行为验证”，本次尚不满足；应发布为明确证据分级的研究版，或继续补实机/试玩记录。不能把标准要求伪称跨作品验证通过。
