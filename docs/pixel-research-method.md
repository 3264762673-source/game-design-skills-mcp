# 像素游戏 Skills 的研究与证据约定

本批次覆盖人物、场景、物品、UI 布局、图标按钮、页面交互、特效动效、人物动作、物品动效九个领域。采用用户选择的**跨作品案例检验**：比较公开的一手资料、独立作品与反例，不声称做过真人实验或还原商业游戏内部实现。

## 起源与工作定义

早期游戏的显示分辨率和颜色资源限制，促使作者在很少的像素中组织形状、层次和识别特征。今天这些约束可以是主动的风格选择。这里把像素美术定义为：在明确的采样网格中，有意识地控制轮廓、色块与关键细节的视觉表达；低分辨率截图本身不构成完整的美术规范。

上述历史背景参考 [Kopf 与 Lischinski，Depixelizing Pixel Art，2011，Introduction](https://johanneskopf.de/publications/pixelart/paper/pixel.pdf)。该论文研究放大与矢量化；它不证明某种像素尺寸、色数或角色设计更好玩。本文的工作定义和 Skill 划分是本项目的工程约定。

像素作品可以采用逐像素绘制、预渲染、骨骼驱动或混合方式。明确项目的显示结果和生产约束，比要求所有作品使用同一种生产流程更有用。原始像素、屏幕像素、CSS 像素和引擎世界单位应分别记录。

## 研究顺序

1. 记录要解决的具体决策、目标任务和可观察失败。
2. 阅读作者教程、开发日志、论文或源代码；在两个不同作品中提出候选规则。
3. 将候选规则写入冻结记录，再查看未用于推导的检验作品。
4. 区分“画面中能观察到”“作者声明”“源码分支可确认”“尚未运行”。记录保留、收窄、否定或无法判断。
5. 把仍有用的规则编译成八字段决策卡，保留例外、预期结果和撤回条件。

独立检验指作品未用于形成该批候选规则，不等于统计独立、盲法实验或多人重复验证。这里的结果只能支持所观察的条件。冻结记录保留原文；后续修改另记修订，避免把检验后的结论包装成事前预测。

## 证据状态

| 状态 | 含义 | 使用方法 |
|---|---|---|
| 跨作品有限支持 | 候选规则与推导、检验作品的明确观察相容 | 在所列条件内作为设计起点；项目效果仍待验证 |
| 收窄后有限支持 | 原规则出现反例，只保留更窄的适用范围 | 必须保留反例和新增条件 |
| 工程建议／待测 | 来源支持机制，但没有足够跨作品行为证据 | 可以提出可撤回试验，不能宣称已经验证 |
| 否定／不采用 | 观察直接冲突，或无法从来源推出 | 留在研究记录，移出推荐规则 |

案例检验既不证明“用了规则导致游戏成功”，也不证明规则必要或充分。截图可以支持视觉组织观察，不能证明点击区域、输入延迟、精确帧长或用户理解率。源码可以支持所读版本中的逻辑判断，不自动代表发行版本和真实玩家体验。

## 八字段决策卡

每条规则写清：**触发条件、候选解释、检查方法、可执行修改、不适用情况、预期变化、验证与撤回、来源与状态**。

检查方法应能区分竞争解释。例如“物品像没被拾取”可能是事件未结算、背包已满、反馈被遮挡或玩家没找到新物品。不同原因不能统一改成“增加粒子”。预期变化写可观察行为；没有玩家数据时写“预期”，不填虚构百分比。

## 来源渠道与权重

- 游戏官网、作者开发日志、公开源码、作者在 Steam／itch 发布的页面：用于归属、生产方法与可定位案例。商店好评不等于设计规则有效。
- 论文：记录读到摘要、正文还是实验部分；区分对该决策的直接证据与相邻领域启发。图像处理论文不能替代游戏体验实验。
- ArtStation、Pinterest：先核查作者、项目和原始出处。转载图板是线索；无法追溯时不承担规则证据。
- YouTube、Bilibili、GDC：分别记录观看、字幕、幻灯片、简介的实际访问层级。未读到点赞或收藏量就标为未核实；不把精选讲者自动称为高赞视频。
- 本次未覆盖所有作品、地区或平台。证据不足的渠道保留缺口，不以搜索结果数制造研究完整感。

## 执行边界

九个 Skill 提供制作决策、交付规格和检查流程，由当前 AI 与已有工具执行。MCP 的 `get_skill` 可读取它们；这不等于新增九个自动绘图或动画生成引擎。既有 Canvas 特效和 UI CSS 工具仍按各自原有契约工作，不自动满足像素渲染约束。

本仓库只发布原创总结、规则和来源链接，不附原书、游戏截图、视频、付费资料或第三方美术资产。研究中的私有工作材料不进入发行包。
