# 体验论：参考游戏拆解与迁移

用“玩家在什么关系中，做了什么，因此把结果理解为什么”描述体验。此技能以用户《体验论》为设计方法；学术研究用于补充或检验局部假设，不宣称为用户理论提供整体科学证明。

## 先定位来源与任务

用户只要研究或 skill 时，交付分析、证据和可执行规格，不自行制作 Demo。已有明确体验和平台约束时沿用；缺失信息写成可撤回假设，只有核心目标存在歧义时才询问。

首次使用读 [方法与来源](references/method.md)。分析具体作品时，区分开发者意图、可观察行为、评论者解释和实际玩家感受。没有操控过游戏，不能把观看评价写成自己的手感体验。

完成条件：作品版本、来源阅读范围、目标载体和本轮交付范围明确。

## 提取体验，而非堆形容词

用一句话填写：当〔处境与关系〕成立时，我通过〔有选择的行动〕造成〔可感知变化〕，因此感到〔变化对我的意义〕。

为核心概念填写：

| 概念 | 本次诠释 | 行为和反馈如何表达 | 玩家可能的另一种理解 | 证据类型 |
|---|---|---|---|---|
| 对手、武器、资源、成功等 | 与玩家的关系 | 至少一个规则结果和一个感知线索 | 共识偏移风险 | 官方/观察/研究/推断/实测 |

把角色能力和玩家能动性分开。角色打得漂亮，不自动意味着玩家感到自己厉害；找出玩家实际选择的时机、方向、风险或接续。

乐趣标签开放使用：欺强、欺弱、掌握、贪念、表达等均需具体诠释。七宗罪仅作可选动机自查，不做人格分类、穷举或百分比分配。

完成条件：每个核心体验有行动、结果、意义；“爽、真实、电影感”能被进一步解释。

## 找到必要条件与因果链

按“处境 → 预期 → 选择 → 系统结果 → 感知 → 诠释 → 后续选择”画出一轮循环。

逐项做删除检验：去掉敌人抵抗、输入选择、风险、受击反应或奖励差异后，目标体验如何变化？这产生候选必要条件，不是心理定律。

优先级按目标贡献、误读风险、可见性、成本排序。用 MDA 辅助检查规则如何形成动态过程，不能把美术风格等同于 MDA 的 Aesthetics。

只有出现理解负担问题时才引入系统层级：先声明主系统原点，按“理解 X 需要先理解 Y”列依赖链。层级深度与一个动作封装的系统数分别记录；沿用项目明确口径，不从有分歧的旧范例推导统一数字红线。

完成条件：可指出核心条件、可替换符号以及去掉条件后的偏移。

## 转成目标载体中的规则

| 条件 ID | 来源关系 | 目标操作/规则 | 反馈与预期含义 | 保留/改变/缺失 | 验证办法 |
|---|---|---|---|---|---|
| C1 | 具体到场景 | 可实施的状态变化 | 玩家凭什么知道 | 显式标注 | 能否推翻假设 |

先做最小闭环规格，说明初始状态、可选行动、触发、结算、终止和失败恢复。把参考作的机制名称与自拟实现字段分开；所有自拟时长和窗口标为试调值。

引入论文时，记录研究任务、样本、操纵因素、结果、限制和对本设计改变的一个决定。观察性研究不写成因果证据；其他品类的实验不能直接给本项目提供最佳毫秒数。

完成条件：另一位实现者能按映射制作，且每项主要规则能回溯到体验目标。

## 分开记录三个结果

1. 来源体验：解释获得哪些证据，哪些仍未知。
2. 迁移状态：候选/部分支持/支持/偏移/未知，并记录条件。
3. 新乐趣：新方案可能好玩，但它是否仍是原体验另判。

用相同场景比较单个因素，保留相反反馈。行为数据、主观描述、性能和不适分别记录；停留时间或再次尝试不能单独证明好玩。

交付体验句、概念表、必要条件、迁移表、最小方案、主要偏移和一个可否定实验。未试玩写“候选映射，实际效果待测”，不阻塞技能交付。


## v0.1.0 MCP 配套

连接 game-design-skills-mcp 后，先用 `list_capabilities` 发现接口，再使用 `get_skill / audit_transfer`。参数以工具 JSON Schema 为准。服务不写文件，返回的代码由调用方在授权项目中接入。结构检查不能证明实际乐趣；通用特效不代表原游戏复刻。未连接服务时按本文执行，不伪造工具结果。
