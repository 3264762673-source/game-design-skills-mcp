# 游戏体验迁移与乐趣记录

以一种具体乐趣为工作单位，例如欺强、欺弱、贪念、嫉妒，帮助用户把它放进另一个可玩的情境。乐趣词是开放的检索标签，其具体含义由本次情境中的诠释决定。

方法来自用户的《体验论》《系统层级论》和已认可的《觉醒邪教徒》范例；本版按后续访谈收窄为体验迁移与乐趣记录。来源和取舍见 [来源与已确认决策](references/sources-and-decisions.md)。

## 工作约定

- 好玩是设计的优先目标。分别判断“原体验是否迁移”和“产生了什么乐趣”；新玩法有吸引力，也可能尚未完成原迁移。
- 创意可以变化；固定的是目标记录、判断依据、状态更新规则。相同前提下的不同判断，应能定位到具体诠释、条件或证据分歧。
- 面向乐趣类型，不预先分类玩家人格、人口属性或七宗罪人群。只记录影响当前诠释的必要认知条件，例如“知道大敌曾经不可战胜”。
- 用户已经给出清晰的目标、范围或批准的诠释时直接沿用。缺失的信息只有在会改变核心乐趣、迁移对象或用户限制时才提问，一轮最多三个关键问题。其余写为可撤回假设并继续。
- 真人试玩由用户后续组织。没有试玩也交付可实施的候选方案和待测记录；如实说明尚未获得实际效果证据。

## 1. 提取本次要迁移的乐趣

首次提取、标签有歧义或来源与目标不匹配时，读 [乐趣与诠释模型](references/pleasure-model.md)。

从已有材料提取：

1. **来源情境**：来自哪个行为、场景、规则或用户描述；注明已看到的材料。材料未提供时，用户描述足以启动，相关机制标为假设。需要外部事实时再核查，不把参考作品的名称当作已经了解它的证据。
2. **乐趣句**：在什么处境下，通过什么行动、变化或见证过程，得到什么值得期待的感受。只写“爽、贪婪、成长”还不足以确定映射。
3. **成立条件**：本次暂定必须保留的关系、能动性、收益/代价、信息知情与揭示时点；只列相关项，标明哪些来自用户、哪些是分析假设。
4. **目标载体与约束**：目标玩法能支持什么操作和反馈，哪些内容必须保留。未指定载体时给一个明确标记为假设的最小载体；存在重大分歧则先问。

把关键概念写成“概念 → 本次含义 → 用什么行为/画面/文本/规则让这一含义可被理解”。共识表示作品传达的含义与参与者理解相合；设计阶段只写“预期共识”，以后的观察才可能支持它。

完成条件：可指出要迁移的具体乐趣、暂定必要条件和目标载体。用户指定的目标保留原文；后续重新诠释时保留修改记录。

## 2. 建立可执行的迁移

对每个必要条件列一条映射：

| 来源的乐趣条件 | 目标规则或行为 | 可感知的反馈与含义 | 保留或改变了什么 |
|---|---|---|---|
| 具体关系或过程 | 触发、选择、状态变化或结果 | 玩家如何获知并解释变化 | 对应 / 部分对应 / 缺失 / 未知 |

可以更换题材、名称、道具和实现方式。是否需要熟悉的符号，由它对乐趣成立的作用决定；逐个替换名词不足以证明迁移成立。

优先给一个能实际执行的最小方案：初始状态 → 可选行动或观察事件 → 状态变化 → 反馈/揭示 → 后续机会或代价。触发、结算时点、持续时间和终止条件写清；必要数值标为初始试调值。多方案只用于确实不同的体验取舍。

检查每个关键条件：删除或替换后，为什么预期乐趣会改变？这只是检验设计假设的方法，不把解释写成已证实的心理规律。

需要范例时读取 [迁移案例](references/migration-cases.md)。范例帮助理解映射，不限定必须做卡牌、飞升、隐藏代价或固定层级。

完成条件：用户或实现者可据此制作最小版本，且每条核心规则能说明它服务于什么乐趣条件。

## 3. 诊断偏差并综合修正

用户提供已有方案、迁移失败描述或试玩反馈时，沿上述映射定位偏差：

- 输入的乐趣含义模糊，或把角色的感受误当成玩家的感受。
- 参考情境并不支持声称的乐趣，存在来源契合度问题。
- 目标方案丢失关键关系、选择、代价或时点。
- 关系在规则中存在，但反馈没有让它可被理解。
- 原体验没有出现，却出现了另一种有价值的乐趣。

这些是候选原因；用现有材料区分事实与推断。给最小修正，并说明改动哪一条映射及预期改变。输入概念不清、范例契合度低可以解释偏移，但不能据此静默改写用户目标。

允许结合其他理论。仅在有具体问题时加载能解释它的资料，说明补充视角改变了哪个设计决定及其待测假设。若环境提供 `game-system-decisions`，规则理解、选择与后果问题可参考它；若提供 `game-feel-experience-design`，操控或反馈传达问题可参考它。两者都是可选配套；本技能独立可用，调用它们不扩大本次范围或新增玩家招募前置条件。

层级、封装和信息负担是辅助诊断。仅沿用当前项目已明确的计数口径与限制；本版不从有分歧的范例推出统一数值红线。方法性红线被实际效果反证时保留具名例外，记录适用情境和证据；用户明确要求不可变的产品约束仍须遵守。

完成条件：偏差与依据可定位，修正有明确作用点。没有足够证据时保留竞争假设，仍可交付候选修改。

## 4. 分开判定原迁移与乐趣

以输入、映射、证据判定，不按“符合理论”自动通过：

| 当前情况 | 原体验迁移判断 | 乐趣处理 |
|---|---|---|
| 必要条件对应，但未试玩 | 候选映射，实际效果待测 | 记录预期乐趣，标为假设 |
| 必要条件缺失或发生核心替换 | 方案发生偏移，不能算原迁移成功 | 记录新乐趣候选，保留原目标 |
| 反馈支持新乐趣，但不支持原体验 | 原迁移未成功或结果不一，依证据注明 | 保留新乐趣及其证据 |
| 只观察到原体验的部分环节，其余未知 | 部分获得支持，原迁移尚未验证成功 | 乐趣是否吸引人另行判断 |
| 反馈支持原体验，但体验并不吸引人 | 原体验出现获得支持，乐趣效果不佳 | 改善玩法或提出改目标，保留两个判断 |
| 两项都得到实际反馈支持 | 仅在本次条件下获得支持 | 记录有效条件与限制 |
| 信息不足或反馈相互矛盾 | 未知或结果不一 | 保留相反证据，不强行定结论 |

“再玩一次”、更长停留、理论检查通过或 AI 模拟，单独都不构成“好玩已验证”。实际反馈按发生的条件记录，不能自动推广到所有人。

当出现新乐趣时，保留新方案并给出继续原迁移、发展新方向或并行保留的建议。用户选定新目标后创建关联的新目标记录；旧目标和未完成状态继续保留。获得用户对原目标的明确替换前，不把新方向冒充原迁移结果。

## 5. 交付与记录

每次交付包含：乐趣句与来源、必要条件、核心映射、可执行方案或最小修正、原迁移状态、新乐趣及证据状态。用简短依据解释判断，按任务大小控制篇幅。

记录格式和后续试玩反馈更新规则见 [乐趣记录](references/records.md)。需要落盘、跨轮更新或机器读取时，从 [JSON 记录模板](assets/experience-record.json) 创建记录，替换空值，保持字段和枚举一致。保存到用户指定位置或项目已有设计记录处；用户要求保存而没有指定位置时使用当前项目的 `design/experience-transfers/`，以唯一记录 ID 命名，不覆盖无关文件。仅在聊天中返回记录时说明未落盘。

没有试玩数据时，附一个可区分主要假设的小实验：改什么、观察什么、什么结果会否定当前解释。它是后续实验建议，不是交付前置条件，也不替用户联系或招募玩家。

完成条件：方案可以实施；原目标与新乐趣可区分；事实、假设和实际效果状态不混淆；记录可供下次继续。技能制作或方案交付完成，不等于体验已经验证成功。


## v0.1.0 MCP 配套

连接 game-design-skills-mcp 后，先用 `list_capabilities` 发现接口，再使用 `audit_transfer`。参数以工具 JSON Schema 为准。服务不写文件，返回的代码由调用方在授权项目中接入。结构检查不能证明实际乐趣；通用特效不代表原游戏复刻。未连接服务时按本文执行，不伪造工具结果。
