# 体验论策划与追问

交付从目标体验到可执行规则的策划规格，同时保留反例、假设和未解决问题。首次使用读取 [方法与契约](references/method.md)；需要机器可复用的问答示例时读取 [示例会话](assets/example-session.json)。

## 1. 建立决策依赖

先读取用户请求、项目和现有方案。能从项目核查的事实先自行查证，引用位置；找不到就记为未知。用户决定取舍，AI 说明建议及理由。用户已说清的目标与约束直接录入，保留原话；不重复询问来制造访谈。

默认决策链：

`范围 → 体验句 → {概念诠释、玩家能动性} → 必要条件 → 行为反馈映射 → 最小闭环 → 否定实验`

依赖按实际问题调整，可添加支线；不要根据未听到的答案推演下游结论。每个决策记录稳定 ID、前提 ID、问题、建议、答案、依据和状态。概念诠释与能动性可以同轮追问，因为两者只依赖已确定的体验目标。

## 2. 追问当前能决定的事

每轮只提出前提已解决的问题。列出整个当前可回答的问题集合；若多到难以回答，可分批呈现同一层，但不越过尚未回答的前提。

每题给出：问题、为什么影响体验、建议及其代价。建议不是用户答案，未回复不算同意。等本轮回答后再重算依赖。

优先追问以下分歧，而非扩写文案：

- “强敌、成长、自由”等概念在本情境意味着什么？玩家看到什么才会这样理解？
- 是玩家作出选择，还是角色在自动表演？删除选择后留下哪种体验？
- 去掉哪项关系或反馈会改变体验？它真是必要条件，还是未经检验的假设？
- 同一行为反馈还有什么合理解释？预期共识可能在哪里偏移？
- 原体验是否迁移、新方案是否有乐趣，分别依据什么判断？

如果用户要求先出草案，明确写出假设后继续候选推演；实际结果仍为待测。用户停止追问时直接整理当前草案和未知项，不强制完成所有支线。

## 3. 回答改变时重查下游

区分 `resolved`（用户决定或有定位的项目事实）、`assumed`（候选假设）、`open`（未解决）。新的上游答案使所有依赖它的旧答案失效：保留于历史，重新开放下游问题，不把旧答案悄悄当成新共识。

保留原始请求。用户改变目标时记录旧目标、新目标和其确认依据；新乐趣单独记录。AI 的理论推导、用户喜欢方案和自动测试均不能证明实际体验。

## 4. 编译策划规格

任何阶段都可交付标明未知项的草案。完整规格需含：目标原话与范围、体验句、概念及另一种诠释、玩家行动与代价、条件 ID、逐条件规则与反馈映射、初始状态/触发/结算/终止/失败恢复、一个能推翻解释的实验。

全部决策解决后，向用户展示整份规格和主要取舍，再记录对当前修订的明确共识。该确认是这次策划访谈的结束条件；不扩大实现、发布或外部操作的授权。用户原本只要设计时，不自行制作游戏。

## MCP 接口

连接 `game-design-skills-mcp` 时：

1. `start_design_interview(original_request, session_id)` 创建结构化问题树。
2. `advance_design_interview(session, answers)` 原子提交同轮回答，返回新 session、当前问题和失效下游。引用原话或证据填写答案；无需把启动问题再问一遍。
3. `compile_game_design(session)` 编译规格，可在未回答完时输出草案。
4. 用户看过当前规格并明确确认后，单独调用 `advance_design_interview(session, [], confirm_revision=当前修订号)`；再编译得到 confirmed 状态。回答与确认不能在同一次调用中提交。

服务不保存会话。调用方保存并传回完整 session；每轮以返回值替代旧状态。MCP 检查依赖、字段和声明状态，不验证自然语言答案是否充分，也不替用户决策。`explore_assumptions=true` 仅允许基于假设继续候选推演，不能把假设升级为共识。

未连接 MCP 时用相同流程在对话或文档中执行。遇到纯数值、状态结构或反馈实现问题，可选用已提供的数值、系统与手感技能；本技能自身不依赖安装其他 Skills。
