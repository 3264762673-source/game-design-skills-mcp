# UI 与布局设计

目标：让用户看懂信息、找到操作、完成任务；让多个页面遵循同一套设计决定。先处理任务与层级，再处理分组、排版和视觉细节。

## 选择任务范围

| 用户意图 | 执行方式 | 完成产物 |
|---|---|---|
| 建立规范 | 识别产品与现有系统，补齐缺失设计决定 | 设计简报、语义 tokens、组件与验收约定 |
| 新建页面 | 明确内容优先级，再实现布局、状态与视觉 | 可运行页面和验证结果 |
| 改善页面 | 定位实际问题，优先修复影响任务的部分 | 有依据的修改与前后验证 |
| 评审页面 | 检查并报告；不自动修改 | 有位置、影响、证据和建议的问题表 |

局部调整只执行相关步骤；无需为了改一个按钮重建设计系统。保留既有技术栈、产品语义和已获授权的范围。

## 1. 建立最小上下文

读取相关页面、已有组件、主题变量及项目设计约定。确认：

- 用户当前要完成的任务、最重要的信息和主要操作。
- 目标设备、语言、信息密度，以及已有品牌方向。
- 框架、样式方案、组件库和已支持的主题。

能从项目推断的直接采用。缺失信息会改变任务或信息结构时才询问；非关键偏好用明确的暂定方案推进。

在实现前留下简短设计摘要：`任务 / 首要信息 / 主要操作 / 内容分组 / 适用屏幕 / 复用组件与 tokens`。修改范围很小时，摘要可以只覆盖受影响部分。

完成标准：能解释用户先看到什么、下一步做什么，以及本次需要改变什么。

## 2. 先组织内容，再确定布局

- 根据任务给信息分主、次、辅助层级；降低竞争信息的强调程度。
- 同一任务区域明确主操作。多个独立工作区可以各有操作层级，不能机械地数全页按钮。
- 用接近关系表达分组，通常组间距离大于组内距离；检查标题是否更靠近它解释的内容。
- 先确定阅读顺序、对齐线和内容宽度，再决定列数。列数取决于内容是否可读，不取决于屏幕还有多少空白。
- 表单和正文限制阅读宽度；表格依据比较任务保留必要信息密度。
- 对新页面或结构混乱的页面，先产出低保真结构或灰度预览。小范围视觉修正不强制增加独立灰度稿。

完成标准：即使去掉品牌色和装饰，信息分组及操作优先级仍清楚。

## 3. 将设计决定落入系统

优先使用已有 tokens 与组件变体。缺少值时先判断能否复用，再有理由地新增语义变量；不要在各页面独立修改同一设计决定。

语义示例：

```text
按钮背景 → color.action.primary → 当前主题的品牌色
辅助文字 → color.text.muted → 当前背景上可读的文字色
字段组距离 → space.form.group → 项目间距阶
```

| 维度 | 默认判断 | 需要结合场景的部分 |
|---|---|---|
| 字体 | 用少量字号和字重表达角色；同角色保持一致 | 中文字体、内容密度、阅读距离 |
| 间距 | 使用有限间距阶，按分组角色选值 | 紧凑表格、触控界面、阅读页面 |
| 颜色 | 按文字、背景、操作和状态定义语义 | 品牌、图表、浅色与深色主题 |
| 边框与阴影 | 用于分隔、浮层或可操作性提示 | 平面风格可以不用阴影 |
| 圆角 | 按组件角色形成稳定规则 | 标签、按钮、容器可以有不同档位 |
| 图标与图片 | 统一图标风格；按内容设置裁切与比例 | 人像、商品图、图表不能同样裁切 |

项目没有规范且用户允许代选时，可用以下起点；这些是示例，不是强制标准：

- 间距阶：4、8、12、16、24、32、48、64 CSS px。
- 正文 16px、辅助文字 14px、标题 24/32px；按实际字体与终端调整。
- 标签到输入框 8px、字段组之间 24px；映射为项目变量。
- 中文正文行高可从 1.5–1.75 试起，用真实段落验证。

完成标准：变化可追溯到组件变体或设计变量；新增值有用途说明。

## 4. 补齐响应式与状态

布局应在目标范围连续变化时可用，不能只让两张截图好看：

- 窄屏重新安排阅读与操作顺序；保留关键内容和主要操作。
- 根据内容开始拥挤的位置设置断点。检查长标题、长姓名、长数字和混合语言。
- 表格确需横向比较时，可使用明确的局部横向滚动；避免整页意外横向溢出。
- 检查固定底栏、浮层、软键盘与安全区域是否遮住内容或操作。

为受影响功能选择适用状态：正常、空数据、加载、错误、成功、禁用、无权限；交互组件还包括键盘焦点、按下与悬停。仅为实际存在的状态设计。

错误信息说明发生了什么、用户如何恢复；加载状态防止不适当的重复提交；空状态给出有意义的下一步。

完成标准：实际任务路径及相关异常路径都有可理解的反馈。

## 5. 分开处理可用性要求与视觉经验

默认按 WCAG 2.2 AA 检查相关 Web 界面要求；这不是完整合规认证：

- 普通文字对比度至少 4.5:1；大字至少 3:1。大字通常指至少 24 CSS px 的常规字，或约 18.67 CSS px 的粗体；不要把任意 18px 文字归为大字。
- 用实际字体、字号、字重及前景背景组合判断。辅助文字也需要可读。
- 状态不能只靠颜色传递；结合文字、形状或图标语义。
- 使用合适的原生语义；表单标签与控件关联，图标按钮有可访问名称。
- 操作可通过键盘完成，焦点可见；对话框等组件按其交互模式管理焦点。
- 触控目标优先设计得宽裕；例如 44×44 CSS px 可作为项目目标。WCAG 2.2 AA 的目标尺寸条款是 24×24 CSS px 或满足相应例外，不能把项目目标与标准混为一谈。
- 支持需要的缩放、内容重排和减少动效设置；对关键任务额外检查窄屏与缩放后的可操作性。

文字颜色数量、字重数量、圆角档位、阴影层数、固定行长均属于设计经验。中文与拉丁文本分别观察阅读效果。项目风格可以偏离经验，但仍需满足已采用的可用性要求。

## 6. 验证与交付

页面能运行时，实际打开并检查。优先用项目目标设备；缺少定义时用 375px 与 1280px 作为初始观察点，再检查中间宽度和内容拥挤处。这不代表覆盖所有设备或完整无障碍要求。

验证应与变更相称：

1. 查看真实内容下的信息层级、分组、对齐、换行和溢出。
2. 操作受影响任务，检查相关组件状态和键盘路径。
3. 对颜色、语义和行为使用可用的自动检查；对视觉与任务效果保留人工或视觉判断。
4. 修复后在相同内容、状态和宽度下复查。

证据分别标为：`截图已观察`、`操作已验证`、`工具检测`、`仅源码推断`。无法运行时明确未验证项；不把源码推断或规则编号命中写成视觉验收通过。

评审问题格式：

| 位置 | 问题与用户影响 | 依据 | 证据 | 建议 | 优先级 |
|---|---|---|---|---|---|

优先级按影响划分：阻止任务或关键信息不可读 → 明显误导、增加操作困难或破坏一致性 → 可选视觉优化。项目已有级别定义时使用项目定义。合并同根因的问题，避免按出现次数堆积报告。

交付说明包含：改了什么、为什么、如何验证、仍有什么限制。建立完整规范时再交付 tokens、使用说明和组件示例；局部修改不要求生成整套文档。

完成标准：请求范围已完成，发现的关键问题已修复或明确报告，所有通过结论都有对应证据。已有设计满足要求时，无需制造修改。
