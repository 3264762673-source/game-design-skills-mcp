# 游戏系统与有意义的游玩

把观察转成候选解释，通过检查选择修改，并规定怎样验证与撤回。以玩家任务和项目的体验意图为判断依据。

## 来源与适用范围

依据用户提供的《Defining the Game: An Introduction to the Formal Systems of Play》教学讲义，讲义注明改编自《Rules of Play》。未读取原书全文。本技能不代表原书完整体系，也不把讲义的定义当作所有游戏的资格标准。

首次使用时读取 [来源与状态](references/source-map.md)。八字段卡片结构来自用户要求；具体检查、修改和指标属于本次工程推导，默认待测。没有项目试玩数据时不能写成“已证实有效”。

## 按任务加载决策卡

| 任务或症状 | 卡片 | 读取 |
|---|---|---|
| 概念只有题材与功能清单，缺少可执行玩法 | SYS-01 系统建模 | [系统设计](references/system-design.md#sys-01) |
| 同一操作何时有效，玩家与设计者说法不一致 | SYS-02 规则预测 | 同上 |
| 难度来自等待、重复操作或与目标无关的阻碍 | SYS-03 挑战与摩擦 | 同上 |
| 玩家不知道任务是否完成、结算理由不清 | SYS-04 结果判定 | 同上 |
| 玩家重复输入、不知道操作是否被接收 | PLAY-01 行动结果可辨识 | [行动与体验](references/meaningful-play.md#play-01) |
| 玩家看懂反馈，却觉得行动不影响后续 | PLAY-02 后果整合 | 同上 |
| 多个选项看起来不同，但实际决策没有变化 | PLAY-03 选择与意图 | 同上 |
| 玩家误解参与条件、角色权限或游戏内外影响 | BOUND-01 参与边界 | 同上 |

一次优先检查与症状直接相关的卡；规则数量不等于覆盖质量。混合问题按因果依赖处理，例如先确认操作被系统接收，再判断反馈是否清楚。

## 工作过程

### 1. 记录意图与事实

明确目标玩家、正在做的任务、预期体验、平台、当前玩法及修改范围。新概念使用最小系统模型；已有项目优先看实际规则、状态和试玩材料。

每条观察写成可复现的行为：在什么状态下，玩家做了什么，系统怎样变化，玩家接着怎样行动。把玩家自述、日志、录像和分析者推断分开。

完成条件：至少有一条可定位观察，或一项明确标记为“尚无玩家证据”的设计问题。

### 2. 排查候选解释

选择卡片，保留相互竞争的解释。缺少日志或可运行项目时，给出需要的最小证据，结论保持为假设。

- 输入没有进入有效逻辑：转入相应技术排查，不用视听装饰掩盖故障。
- 输入已接受但玩家看不懂结果：检查 PLAY-01。
- 结果看得懂但不影响后续：检查 PLAY-02。
- 后续影响存在，但不符合玩家想要的体验：回到设计意图，不自动增加复杂度。

完成条件：说明已排除什么、仍不确定什么、证据为什么支持下一步。

### 3. 提出或实施最小修改

按用户授权选择建议、原型或实际改动。保留不相关数值与内容；能通过单一改动区分解释时，避免同时改变数值、音效、奖励和教程。

每条决策采用八字段：

1. 触发条件。
2. 候选解释。
3. 检查方法。
4. 可执行修改。
5. 不适用情况。
6. 预期变化。
7. 验证与撤回。
8. 来源与状态。

卡片给的是候选方案。检查不支持它时，记录“不适用”并选择其他解释。

完成条件：能指出修改作用于哪个规则、状态或可见结果，以及它为什么有望改善观察到的问题。

### 4. 验证并作决定

需要验证效果时读取 [试玩记录模板](references/playtest-template.md)。先定义目标行为、计数口径、比较条件和撤回条件，再测试。

复现修改前的问题，使用可比的任务、难度、角色和输入条件验证修改后表现。随机机制可用相同种子做机制复现，同时用其他种子检查泛化；真人重复试玩要记录学习效应或调整版本顺序。

规则测试、日志、AI 模拟只能证明其实际覆盖的部分；不能代替目标玩家是否理解、是否喜欢的证据。小样本提供方向性线索，不写成普遍结论。

没有合适玩家或测试环境时，交付可执行测试计划并标记待测，不伪造实测通过。

完成条件：给出保留、继续观察或撤回的决定；包含证据、局限与下一步。实际修改应能定位到改动版本，以便撤回。

## 判断边界

- 本讲义支持用“对象—关系—规则—情境”分析系统，不提供完整生产流程、经济模型或难度公式。
- 冲突可以是空间、时间、资源、解题或多人协作中的阻力，不要求加入敌人或竞争。
- 可判定结果不等于必须有分数、输赢或全局终局。开放式创造与自由游玩按其目标检查局部状态或用户自定成果。
- 结果可辨识不等于每次输入都有更强粒子、震屏或数字；后果整合也不等于加永久成长。
- 隐藏信息和延迟结果可以是设计意图。检查公平的预期与适当揭示，保留悬念。
- “魔法圈”是理解约定的概念工具，不意味着游戏不会产生真实社交、经济或身体影响。

## 交付

简述观察、主假设、排除依据、所用卡片和最小修改；附八字段决策及验证状态。新玩法可附最小系统模型，诊断任务不强行重做完整设计文档。

来源用本讲义的段落定位，不编造原书章节与页码。将“讲义观点”“工程推导”“项目观察”“项目实测结果”分别标识。只有通过实际验证的具体项目结论才能标为项目实测。


## v0.1.0 MCP 配套

连接 game-design-skills-mcp 后，先用 `list_capabilities` 发现接口，再使用 `audit_system`。参数以工具 JSON Schema 为准。服务不写文件，返回的代码由调用方在授权项目中接入。结构检查不能证明实际乐趣；通用特效不代表原游戏复刻。未连接服务时按本文执行，不伪造工具结果。
